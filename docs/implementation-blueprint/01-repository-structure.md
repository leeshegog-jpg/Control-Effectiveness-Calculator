## 1. Repository Model

**Monorepo**, not polyrepo. Justification: the frontend (OpenAPI-generated client), backend (OpenAPI producer), database schema, and ontology are tightly coupled and must move together — the platform's central defect being fixed (Design Baseline v1.0, architecture doc §1.4) is exactly the fragmentation that comes from independently-versioned artefacts drifting apart. A monorepo with clear internal package boundaries enforces the single-source-of-truth principle the architecture already commits to. This is an implementation-planning decision within the frozen architecture, not a change to it.

## 3. Folder Purpose — Detail

| Folder | Purpose | Owner discipline |
|---|---|---|
| `apps/web` | React + TypeScript frontend — every UI module from the architecture's Client subgraph (Executive Dashboard, SMS Module Views, Hazard Knowledge Library, Major Hazard Register, Risk Management Engine, Critical Control Management, Document AI UI, Knowledge Graph Explorer, Bow-Tie/MoC Diagrams, AI Gap Analysis, Safety Case Workspace, Safety Case Demonstration Engine UI, Ontology Curator UI) | Frontend |
| `apps/api` | FastAPI backend — REST/GraphQL API, AuthZ, Ingest, Extraction, Graph Sync, Gap Analysis, Ontology, Demonstration Generation services (architecture §2 API subgraph) | Backend |
| `packages/shared-types` | Generated, never hand-edited — single source of truth is `10-openapi.yaml`; regenerated by CI on every OpenAPI change | Platform |
| `packages/api-client` | Typed fetch wrappers over `shared-types` | Frontend |
| `packages/ontology-client` | Wraps ontology concept lookup/validation so no module re-implements "resolve this string against the live concept list" independently — the exact failure mode that produced V1's four incompatible category lists | Platform |
| `packages/ui-components` | Shared shadcn/ui-based components, one design system across every module | Frontend |
| `ontology/` | Ontology *content*, distinct from `apps/api`'s Ontology Service *code* — concept definitions are data under governance (EKG spec §6), not application logic | Ontology curator (VRTP HSE), not developers |
| `database/postgres/migrations` | One migration per schema change, generated via Alembic, reviewed like code | Backend |
| `database/neo4j` | Constraints/indexes as versioned artefacts (02 §5); instance data is *not* migrated here — it's synced from Postgres by the Graph Sync Service at runtime, so this folder stays small | Backend |
| `infrastructure/bicep` | Azure resource definitions — Container Apps, PostgreSQL Flexible Server, Blob Storage, Key Vault, and the Neo4j/Qdrant hosting decision made in Phase 2 scaffolding (architecture §8) | Platform/DevOps |
| `tests/graph`, `tests/ontology` | Executable form of [06-relationship-rules-catalogue.md](../knowledge-graph/06-relationship-rules-catalogue.md) and [07-inference-rules-catalogue.md](../knowledge-graph/07-inference-rules-catalogue.md) — every business rule in those documents becomes a test here, not a comment | QA/Backend |
| `tests/ai-extraction` | Golden-set documents with expected extraction output, testing against [04-ai-extraction-specification.md](../knowledge-graph/04-ai-extraction-specification.md) §6 confidence routing | AI/Backend |
| `.adr/` | One file per architecture *decision made during implementation* (e.g. "why Alembic over raw SQL migrations") — not for decisions already fixed in Design Baseline v1.0 | All disciplines |
| `.acr/` | Formal change requests against the frozen baseline — see [02-development-standards.md](02-development-standards.md) §7. Empty at Phase 2.1 start; its presence is itself the control that stops silent architecture drift |
